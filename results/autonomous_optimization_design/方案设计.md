# 固定模型、精度和硬件下的 LLM 推理软件自主优化方案

## 1. 目标与主张

目标是让 AI 提出**可执行的推理执行计划**，由程序验证约束、运行仿真、维护 Pareto 前沿，并将少量候选交给数值与实机验证。不要把“AI 改任意代码后得到更低模拟延迟”作为成功标准。

首个研究对象：当前 RoofLang 的 DSV4 Flash、单节点 8 × B300、Decode。设计两类软件架构：

- **A：拓扑感知的分布式执行架构**。改变合法的 CP/DP/EP/PP 划分、层到阶段及专家到已有 GPU 的映射，联合处理数据所有权与通信。
- **B：依赖感知的异步执行架构**。保持算子与数据布局，改变独立分支的 stream 分配、依赖同步及并发窗口，让网络传输与独立计算重叠。

**主攻 B，A 作为强基线和后续外层搜索。** B 的第一阶段只允许改变独立算子的 stream，保留原有数据边、控制边、精度、资源上限、张量与硬件。将来再加入显式预取与缓冲管理。这使首个实验的因果关系清楚，也更容易对应 CUDA stream/event 的真实实现。

这不是限定长期只做调度。执行计划一旦可靠，后续可扩展到融合、布局、算子实现等更大的软件设计空间；不建议第一阶段同时开放这些动作。

## 2. 固定项与评测口径

| 固定项 | 约束 |
|---|---|
| 模型语义 | 使用 dsv4_flash 当前模型定义，43 层、D=4096、256 专家、TOPK=6；不减层、不改路由、不减少 Attention/KV 访问语义 |
| 精度 | 保持当前张量 dtype 和算子精度选择：路由专家 FP4、共享专家相关投影 FP8、相应激活 BF16；不把更低精度当作软件收益 |
| 权重与输入 | 相同 checkpoint、请求/输入、随机种子和解码策略；实机比较需冻结模型文件哈希 |
| 硬件 | 同一 B300Cluster(1)，8 GPU，固定算力、容量、链路带宽与延迟；禁止通过修改硬件预设优化分数 |
| 工作负载 | 首例 B=512、历史长度 8192、Decode 单步；同一候选比较时 B 和上下文不变 |
| 计时边界 | 统一 read_input 到约定输出完成点；KV preload 单列；输出后的必要尾部工作单列，持续服务时不能无故排除 |
| 内存 | 同时计常驻权重、KV、活跃中间结果、通信/预取缓冲；使用活跃期峰值，不用张量大小简单相加代替 |

语义不变和 dtype 不变，不自动意味着浮点结果逐位相等。第一阶段改变独立分支 stream、不改算子及归约顺序，以确定性实现的逐位一致作为优先目标。涉及归约、融合或内核更换的动作，必须另行制定数值误差和模型输出验收标准；没有通过之前不得进入可接受候选集。

RoofLang 的 graph.validate()/placement.validate() 验证图和放置约束，**不执行模型数值，也不构成完整数值等价证明**。

## 4. 架构 A：拓扑感知的分布式执行

### 4.1 结构

模型图 → 并行分组与层划分 → 专家/算子/张量映射 → 显式通信图 → 执行。

仍使用同一批 GPU。改变的是软件怎么把工作和数据分给这些 GPU，不改变芯片微架构。

### 4.2 动作与代价

| 动作 | 前置条件 | 额外计算 | 额外显存 | 通信变化与代价 | 适用场景 |
|---|---|---|---|---|---|
| 修改合法 CP/DP/EP/PP | 当前优化器约束 CP×DP=EP、EP×PP=8；PP 层数和=43；batch/上下文满足各项可整除约束；放置有效且不 OOM | CP 中被复制的 Q 等路径可能增加计算；PP/DP 需按实际图计量 | 权重/激活复制、KV 分片和活跃期随计划改变，不能默认恒定 | CP 广播/归约、EP 路由、PP 边界传输必须显式保留 | 长上下文、内存压力、明显负载不均 |
| 改变 PP 层边界 | 保持层顺序和残差/KV 生命周期；阶段数固定时每阶段获得相同规则的设备组 | 算术总量通常不变；不能假设气泡已消失 | 改变每阶段权重/KV/激活负载；流水并发另需缓冲 | 跨阶段激活和同步，边界改变可能改变关键路径 | 层成本差异明显，例如不同压缩比层 |
| 改变专家所有者/设备排列 | 每个专家权重正确归属，路由和合并端口同步重建；不能只改设备而遗漏传输 | 不迁移算术定义；必要打包/解包应计入 | 冷启动迁移、重配置时临时双份权重需要计量 | 可降低跨节点流量，也可能增加热点；原地放置变化的初始化成本另列 | 多节点异构链路、不均衡专家流量；单节点对称 B300 上收益可能很小 |

当前 8 GPU 的均匀 PP 基线共 10 类 CP/DP 组合：PP=1 有4种，PP=2有3种，PP=4有2种，PP=8有1种。Flash 均匀层划分分别为 [43]、[22,21]、[11,11,11,10]、[6,6,6,5,5,5,5,5]。这是受约束搜索空间，不是所有软件架构的穷举。

第一阶段把 A 当作强基线：使用已有搜索即可。仅复现 CP/DP/EP/PP 参数扫描，创新性有限，不建议作为“自主软件架构优化”的全部内容。

## 5. 架构 B：依赖感知的异步执行（主攻）

### 5.1 结构

保留算子 DAG 和布局 → 找到可独立推进的分支 → 分配 stream → 用原有依赖同步 → 仿真资源竞争与缓冲生命周期 → 输出可回放计划。

首个候选是 MoE 的两条已有分支：

- routed 分支：专家结果到达后的 TokenCombine，可能受远程读限制。
- shared 分支：共享专家的 down GEMM，主要使用本地计算/HBM。
- 两条分支最终由 moe_add 合并。

这两条分支在语义上可以独立执行，但真实能重叠多少还取决于它们各自输入何时就绪。最小用例先固定输入都已就绪；整模型必须保留真实上游依赖。

### 5.2 动作与代价

| 动作 | 前置条件 | 额外计算 | 额外显存 | 通信变化与代价 | 适用场景 |
|---|---|---|---|---|---|
| 将独立 shared 分支放到另一 stream | 分支无相互数据依赖/副作用冲突；保留 join；有足够资源与显存 | 算术 FLOPs 不变；实机增加调度/event 成本 | 并发输出/中间值活跃期重叠，峰值可能增加 | 传输字节不变，但并发可能造成链路/HBM 竞争 | 一个分支受网络限制、另一分支本地计算/访存，且有就绪重叠窗口 |
| 限制并发窗口/stream 数 | 知道活跃张量与峰值预算；避免无限排队 | 算术不变；可能增加等待 | 限制临时缓冲和并发峰值，代价是隐藏延迟变少 | 降低突发竞争，可能增加总完成时间 | 接近 HBM 容量或多请求争用 |
| 调整 resource_cap（后续） | 需明确真实后端可实现的机制；当前仅模拟抽象，不默认等于 CUDA stream priority | 不改 FLOPs，改变推进份额 | 生命周期随持续时间变化 | 设备资源份额变化不等于网络带宽份额变化 | 分支长短不均时的模拟探索；实机能力确认前不作为首期动作 |
| 显式预取/双缓冲（后续） | 数据源不可变或有版本约束；复制完成有依赖；有空闲缓冲；算子尚未消费 | 增加复制/打包工作，按真实实现计费 | 双缓冲上限约为额外一份块缓冲，具体取决于分块和生命周期 | 可能提前发送原有流量，也可能增加中间复制；不得把复制省略 | 数据到达慢、存在足够独立计算、缓冲容量允许 |

不允许删除必要依赖、缩短 KV 读范围、减少专家路由、降低 dtype、提高虚构硬件带宽，或仅更改评分公式。

### 5.3 为什么选 B

1. 直接承接此前的 TokenCombine 例子，能解释到算子和 trace。
2. 现有 Placement 已支持 stream；无需先实现融合内核或新硬件。
3. 第一动作只修改执行计划，容易隔离语义、算术量和通信字节是否变化。
4. 现有 overlapped 指标只能做参照；显式调度能检查是否真的有依赖就绪窗口、是否 OOM、是否争用。
5. 可映射到真实 stream/event，但必须用真实执行器验证；模拟器不会自动提供这一步。

## 6. AI 自主优化闭环

AI 只提交结构化动作，不允许修改模型、硬件和评分器源码。

首期动作格式示例：

```json
{
  "operator_id": "layer0.shared_down.dp0",
  "action": "set_stream",
  "from_stream": 0,
  "to_stream": 1,
  "hypothesis": "与独立的 routed Combine 重叠，原有 moe_add 依赖保持不变"
}
```

工作流程：

1. 从 baseline trace 提取关键路径、等待原因、计算/访存/网络时间、链路占用与活跃内存。
2. AI 从白名单提出少量动作与可检验假设，例如“该分支提前运行，消除 X 的 stream 等待”。
3. 确定性构造器应用动作；拒绝非法 ID、依赖破坏、精度/硬件变更以及不可回放动作。
4. 运行 graph/placement 验证，比较冻结契约；执行模拟器，记录 OOM、错误、完整 trace、FLOPs、链路字节与峰值。
5. 候选不只与最初基线比较，还要与规则策略和同等预算的随机搜索比较。
6. 将合法非支配候选放入档案；以 canonical action/graph/placement hash 去重。
7. 停止条件：预先给定评估预算、无改进轮数或时间预算。每个结果绑定 commit、输入配置、动作序列和随机种子。
8. 少量入围候选进入数值/实机验证，实测结果反哺模拟器误差分析。

第一版不需要复杂强化学习：从少量白名单动作加可解释反馈开始。必须记录 AI 提案相对随机/规则搜索的有效率、单位评估预算收益，否则很难证明 AI 的价值。

## 7. 指标与 Pareto 口径

固定 batch 的单步 Decode 中，tokens/s/user 与 tokens/s/GPU 都由同一个完成时间推导，不能把二者当作互相独立的优化目标来制造“前沿”。

第一阶段对同一工作负载用：

- 最小化显式仿真输出完成延迟；
- 最小化峰值 HBM，或把峰值作为硬约束；
- FLOPs、每链路字节、链路拥塞、错误/OOM 作为解释和约束。

跨 batch 的吞吐—交互速度曲线：可使用 B∈{8,64,512,2048} 分层评测，同一 B 下先比较候选；之后形成跨负载曲线。agent 不得通过改 B、请求长度或计时起止点让单次候选“获胜”。首阶段只做 Decode 8K，稳定后再加 32K、Prefill 和混合流量。

对最终服务系统报告 TPOT/TTFT 的 p50/p95/p99、SLO 内吞吐和并发容量；这些需要请求到达模型或真实服务压测，当前单步静态图不直接提供。

不得把 elapsed/overlapped 投影当作显式执行性能，也不得把主机跑模拟器的 wall time 当作模型推理时间。

## 8. 已完成的最小验证

### 8.1 片段与边界

脚本 minimal_validation.py 使用真正的 TokenCombine、Gemm、ElementwiseOp 类及 B300Cluster(1)。构造 DSV4 Flash 的一个 MoE 片段：

```
来自 8 GPU HBM 的专家结果 → TokenCombine ─┐
                                        ├→ moe_add
共享专家 up 的输出 → shared_down GEMM ───┘
```

M=64，D=4096，MOE_INTER=2048，专家数256，TOPK=6。它对应全局 B=512、DP=8 的一个局部分片；并非完整 43 层模型。所有根输入在 t=0 已就绪；其余 GPU 提供远程输入，但没有模拟其他 DP 分片的并发计算/通信。没有额外假设真实全模型中两个分支必然同时就绪。

Baseline：三个算子都在 GPU0/stream0。Candidate：只把 shared_down 放到 stream1，其余完全相同。

不执行 tensor 数值或 CUDA kernel；这是调度机制和模拟约束验证，不是实机加速或数值等价验证。

### 8.2 可复现结果

| 用例 | 单 stream，μs | 双 stream，μs | 结论 |
|---|---:|---:|---|
| 远程 Combine + 独立 shared_down | 4.445239 | 3.261297 | 片段延迟降低 26.63% |
| 输入全部本地，两分支竞争本地资源 | 1.860443 | 1.860443 | 多 stream 不自动带来加速 |
| 增加明确的 combine→shared_down 控制依赖 | 4.445239 | 4.445239 | 更换 stream 不能绕过依赖 |
| 显存预算位于两者峰值之间 | 完成 | OOM | 有收益的调度仍可能因容量不可接受 |

正例中 GPU0 峰值：9,961,984 B → 10,093,056 B，增加 131,072 B，即128 KiB。FLOPs 和总链路 byte-hops 均不变；注意 byte-hops 是逐链路字节相加，不等于唯一 payload。

容量反例把模拟容量缩小为测试夹具中的可用预算，并在同一预算下比较两种调度。它仅验证拒绝机制，不是宣称真实 B300 只有约10 MB，也不纳入固定 B300 硬件的性能收益。

### 8.3 自动检查

- graph.validate()、placement.validate() 均通过；
- 每对 baseline/candidate 的冻结契约 hash 相同：算子属性、shape/dtype、依赖、设备/内存位置、算力、容量、链路和读取比例都不变，唯独 stream 可变；
- FLOPs 和链路字节一致；
- 每条数据/控制依赖都满足后继开始时间不早于前驱完成；
- 正例有加速，本地争用/强制依赖反例没有虚构加速；
- OOM 候选被明确拒绝。

这些检查证明这个片段中动作只改变调度，并遵守当前模拟器约束；不证明所有后续动作自动等价。

### 8.4 运行

在仓库根目录运行（Python 环境需安装 RoofLang 依赖）：

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$(pwd)/.." python \
  results/autonomous_optimization_design/minimal_validation.py \
  --output-dir results/autonomous_optimization_design/validation
```

输出 results.json、results.csv；预期 checks=PASS。独立脚本调用当前库，不修改仓库模型、模拟器或现有搜索脚本。

## 9. 后续最小整模型验证

下一步不是把26.63%写成整模型收益，而是：

1. 使用完整 dsv4_flash、43层、固定8×B300与工作负载，保存 baseline trace。
2. 只给 shared 分支分配独立 stream。若只改 shared_down 仍被原 stream 上的上游阻塞，再把完整 shared 分支作为一个受依赖保护的动作单元；原 join 不变。
3. 明确处理 split 生成的通信节点：当前通信 stream 会从前驱推断，不能认为只改一个下游节点就能把整段通信放到独立 stream。
4. 保留 KV preload、最终采样和输出后尾部约束；报告原始输出延迟、总 makespan、峰值、所有共享链路流量。
5. 做 B=8/64/512/2048 对照，先逐点比较，再比较负载曲线；OOM/不改善也作为有效结果保存。
6. 只保留跨工作负载有效且满足内存预算的候选，进数值/实机阶段。

如果完整图没有可用重叠窗口，应接受该假设被否定，分析原因；不能删除依赖来复现片段收益。转而检查分块预取或回到 A 的布局优化。

## 10. 数值与实机验证门槛

三个层级必须分开报告：

1. **结构合法**：IR/Placement 检查及冻结契约。当前最小用例已完成。
2. **数值正确**：使用同一权重和输入运行 baseline/candidate；检查目标中间张量、logits、采样和 KV 状态。先启用确定性内核和固定随机种子；数值容差须预先定义，不能看结果后放宽。当前未完成，RoofLang 本身不执行这些值。
3. **性能有效**：真实 GPU 后端实现对应 stream/event；warm-up 后重复测量，固定输入、并发、GPU频率/功耗设置等可控条件，计所有必要同步和缓冲。测量 p50/p95 及波动；数值失败的结果不计收益。当前未完成。

先做一个目标 MoE 片段的真实执行器，再集成完整推理框架。最小 PyTorch/CUDA 原型可以验证调度机制，但若没有相同 FP4/FP8 内核和数值路径，不得用替代 BF16 实验声称目标模型的精度/性能已经验证。

当前模拟器理想化计算峰值、通信重叠、调度开销和精细资源竞争；不能根据一个模拟收益比例保证真实加速。特别关注：微小 kernel 的启动成本、stream 并行的真实 SM/HBM 分配、通信库占用、缓存和带宽校准，以及更多在途请求引起的内存峰值。

## 11. 实施计划与验收

建议按约10个工作日的原型节奏分阶段推进；这不是对实机集成时间的保证，后端和设备可用性会影响工期。

| 阶段 | 建议投入 | 交付与退出标准 |
|---|---|---|
| 范围冻结、基线、两类架构与动作表 | 1–2天 | 固定契约、计时口径、可复现 baseline；本方案已提供初版 |
| 机制 MVP 与正反例 | 1–2天 | 正例+资源/依赖/容量反例；本方案已跑通片段版本 |
| 整模型显式调度动作 | 2–3天 | 真实依赖/通信推断下的完整 trace；没有数值声称；改善或失败原因均可复现 |
| 规则/随机/AI 同预算对照 | 2–3天 | 固定评估预算和种子；比较合法率、最佳可行延迟、Pareto 档案和评估次数 |
| 后端验证设计与首个执行器 | 另行排期 | 数值正确后测实机；设备/内核未到位时明确标记 blocked，不伪造指标 |

建议首期验收目标：

- 两类架构都给出至少两项可定义动作及前置条件/成本；不要求一次全部实现。
- 主攻 B 至少实现一个可回放动作，具有正例、无收益反例和容量/依赖约束。
- 完整图实验至少覆盖多个 batch；不能仅报告最好的一点。
- AI 与规则/随机搜索比较使用相同预算，提供失败候选与拒绝原因。
- 所有候选绑定完整配置、commit、动作序列与日志；可重新运行。
- “模拟改善”“数值通过”“实机改善”分栏，不把前者写成后两者。

## 12. 汇报建议

用一张架构图讲清“AI提案→动作构造→约束检查→显式仿真→候选档案→数值/实机验证”，再用本次三算子 MoE 片段演示一个有效动作和一个失败动作。

推荐表达：

> 我们固定模型、精度和硬件，研究分布式布局与异步执行两类软件架构，优先做依赖感知的通信计算重叠。AI提出受约束的执行计划，验证器保证候选不改变冻结项，模拟器检查资源竞争和内存代价。当前已完成一个MoE片段的正反例验证：仅更改stream，模拟延迟降低26.63%，代价是128 KiB额外峰值内存。下一步验证真实整模型依赖下是否仍成立，并用数值和实机结果校准。
