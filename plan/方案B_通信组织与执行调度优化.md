# 方案 B：通信组织与执行调度优化

日期：2026-10-28  
项目：`/mnt/nvme1n1/data/lmk/PROJECT/TEST2/rooflang`  
性质：设计与可行性分析；仅依据现有代码和已读取结果，未开展新的实验。

配套主路线：[方案 A：DCP 与混合并行优化](方案A_DCP与混合并行优化.md)。

## 1. 结论与定位

本方案作为第二类软件架构设计，优先考虑Query投影复制、通信打包和显式缓冲布局；复杂多batch调度、任意算子融合不宜作为首版重点。

相对当前CP1最优前沿，通信比例较低，而且评分已经采用理想overlap。仅增加通信重叠很难形成30%的可信收益。真实kernel优化可能有收益，但当前roofline模型无法充分预测launch、占用率和形状效率。

因此本方案适合作为DCP路径的增强，不应独立承担整个课题30%指标。

## 2. 固定条件

- 固定Kimi K3模型语义、权重、精度及GB300 8 GPU。
- 不删除必需依赖，不减少专家、head或context，不通过降低精度换速度。
- 复制、融合、重排和重叠都必须保持输出及状态更新契约。
- 所有候选显式记录额外权重、激活、通信和临时缓冲。
- 使用冻结的评价协议，不能在观察候选结果后切换评分制造提升。

## 3. 当前项目基础与限制

| 能力 | 代码入口 | 含义 |
|---|---|---|
| stream与资源份额 | `language/placement.py` | 可放置独立并行工作 |
| 离散事件、资源竞争 | `runtime/simulator.py` | 同stream串行，重叠任务竞争资源 |
| AllToAll等通信 | `language/kernels/comm.py` | 可复用通信表达 |
| 通信图优化 | `language/optimization/comm.py` | 已有图级化简基础 |
| FLOPs、访存计费 | `language/kernels/kernel.py` | 可表达减少中间读写 |
| Pareto计时投影 | `programs/experiments/find_pareto_frontier.py` | 包含理想overlap上界 |

当前计算时间主要由FLOPs/设备峰值决定；本地时间还受访存约束。该模型不能自动捕获真实小矩阵kernel效率、launch开销、寄存器压力及具体通信后端差异。

现有通信抽象也不能仅通过更换后端名称就预测FlashInfer/NVLS等实现收益。若缺少实测或可靠来源，后端差异必须作为未校准因素说明。

## 4. B1：Query复制与packed通信

### 机制

在完整TP/DCP路径中，以每rank复制所需Query投影权重及本地投影，减少运行时Query交换；把attention局部输出和LSE组织为一次打包通信，再本地合并。

```text
增加部分投影权重和计算
    → 减少Query通信与同步
    → packed输出/LSE交换
    → 精确merge
```

### 前置条件

- 已有可信TP/DCP和KDA布局，不能用当前CP参数改名代替。
- 明确DCP组内Query head范围、权重精度、量化scale和归属。
- 显存可容纳复制权重、输出/LSE以及打包缓冲。
- 后续投影需要的head布局与通信输出一致。
- 精确LSE合并的数值契约成立。

### 成本与预期

| 项目 | 影响 |
|---|---|
| 额外计算 | 重复Query投影及可能的打包/merge |
| 额外显存 | 复制权重、量化scale、通信缓冲 |
| 通信变化 | 减少Query交换；保留输出/LSE交换 |
| 适用 | 通信同步较贵、Query计算能承受、互联较快 |
| 不适用 | 复制权重触发OOM、计算开销超过通信节约 |

这是B中最容易在rooflang中解释的变换，因为主要成本可以用FLOPs和字节明确表示。但相对当前DPA/CP1基线，没有DCP Query通信可以直接消除；它的价值主要来自增强新的DCP候选。

在方案A基础已经完成时，估计3–5人日。不能把A的前置工程成本省略后声称完整方案仅需几天。

## 5. B2：stream调度与计算通信重叠

### 机制与条件

对无数据依赖冲突的分支安排不同stream，使本地计算和网络通信并行。若必须先消费通信结果，则需分块流水或多batch，而不只是修改stream编号。

合法性检查必须覆盖：

- 数据、控制及状态写入依赖；
- 缓冲生存期和读写冲突；
- 多batch的KV和KDA状态隔离；
- 计算、HBM和网络竞争；
- 输出完成时刻，不能只优化某个GPU的局部结束时间。

额外代价包括缓冲、分块管理、资源竞争和更多小任务。KDA为有状态计算，不能把跨token更新任意并行化。

### 当前评分冲突

现有Pareto的理想overlap估计，会在每卡elapsed中扣除本地工作与暴露通信的较小者，再推算stage周期。它不是已经实现的stream或多batch调度。

如果继续以该理想指标评分，再实现重叠可能看不到新增收益；如果再次扣除通信，则构成重复计算收益。

本方向需要预先建立协议：

1. 可执行DAG与调度得到的elapsed为主指标。
2. ideal-overlap作为潜力上界单独报告。
3. 基线与候选使用同一协议评估。
4. 为重叠新增的缓冲和状态副本全部计入峰值。

### 收益上限

既有CP1结果的通信占比约为几个百分点。例如此前128K、batch128的CP1通信统计约0.89%。该比值不是严格关键路径占比，但已不足以支持“仅隐藏通信可提升30%”的判断。

简化地，若能消除的关键路径比例为f，整体加速上限为 `1/(1-f)`。f为3%时，上限约1.031。要达到1.3，至少需23.1%的可消除路径。

不能先人为选择通信较差的CP8配置，再把改善到CP1水平解释为超越现有最优前沿。

### 工期

- 有限独立分支的stream调度：约4–7人日。
- 分块、多batch、状态和缓冲生命周期：约10–20人日。

第二项已经是复杂架构开发，建议首版暂缓。

## 6. B3：算子融合与小矩阵kernel优化

真实执行中，融合可以减少launch和中间访存，专用kernel可以改善小矩阵效率。但rooflang当前理想峰值模型不能完整表达这些收益。

| 优化来源 | 当前可表达程度 |
|---|---|
| 减少显式中间HBM读写 | 较高，需验证融合可实现 |
| 减少FLOPs或重复操作 | 较高，必须语义等价 |
| 减少launch成本 | 当前读取的计时路径缺少专门模型 |
| 提高占用率、矩阵形状效率 | 缺少形状相关效率模型 |
| 寄存器/共享内存容量限制 | 不能由简单字节减少自动验证 |

不能假定任意融合都能把中间张量免费放在片上，也不能直接设置“融合后快30%”系数作为验证。

有依据的融合表达约5–10人日；真实收益预测需要额外校准，当前不能给出可靠工期或性能承诺。该子方向暂不建议作为主攻。

## 7. Agent需要怎样改变

现有 `agents/find_pareto_frontier/AGENTS.md`：

- 只允许修改模型optimization和实验目录；
- 禁止language/runtime和代价模型变更；
- 禁止非默认stream；
- 优化overlapped前沿；
- 要求全域复验和很强的理论停止条件。

该任务模板不能直接完成B2，也不足以补齐B1所需新原语。应先由开发层建立合法动作，再让搜索Agent选择，不能让Agent随意改变性能计费或正确性标准。

建议首版动作：

```text
query_projection_replication = on/off
partial_output_exchange = 经验证的通信实现
buffer_layout = 经验证的布局
schedule = 经验证的有限独立分支模板
```

“经验证”意味着明确张量、状态、依赖和成本，而非仅为动作取一个名字。

## 8. 闭环原型与运行成本

复用现有Agent启动、仿真进程、结果JSONL和Pareto实现。新增结构化候选、确定性合法性检查、失败归类、版本化缓存、预算及规则/随机搜索对照，约6–12人日。该成本与方案A共享，不应重复计算。

闭环：候选 → 合法性检查 → 仿真 → Pareto更新 → 瓶颈/失败反馈 → 下一候选。

现有部分case墙钟约100–180秒，按这个历史量级粗估100个候选需约3–5小时串行计算。未来新图和主机竞争会改变耗时。不能将此估算当成固定运行速度。

建议预先固定候选预算，分阶段筛选，最后统一验证。缓存键应包含代码和评价版本，避免旧计费结果污染新前沿。

自主优化有效性要与规则、随机搜索在相同评估预算下比较；架构性能收益与搜索效率收益分别报告。

## 9. 后续最小验证计划（本次未执行）

### B1

比较Query复制前后的数值、权重占用、计算量和通信量，检查量化scale、head布局和LSE缓冲；覆盖复制引起OOM的边界。

### B2

构造有独立分支与无独立分支的两类小图，检查合法并行、依赖保持、资源竞争及缓冲峰值。不能把ideal-overlap当成可执行调度测试的期望结果。

### B3

若后续启动，先挑选有明确中间读写节约且可实现的融合，单独验证语义和内存代价。无可信校准时不报告真实kernel加速百分比。

## 10. 决策表与退出条件

| 子方向 | 工程可行性 | 相对当前最优点30%证据 | 决策 |
|---|---|---|---|
| Query复制与packed通信 | 高，依赖DCP基础 | 单独不足 | 优先作为A的增强 |
| 有限stream重叠 | 中高 | 通信占比和评分限制明显 | 次要方案 |
| 多batch/分块调度 | 可行但复杂 | 需明确关键路径空间 | 首版暂缓 |
| kernel融合/效率优化 | 抽象可做，预测能力有限 | 无校准难证明 | 暂缓 |

当通信关键路径不足、理想上界已覆盖候选收益，或只能通过修改代价常数得到提升时，应停止投入相应分支。

方案B的价值是完善软件架构设计的第二类路线、增强DCP候选，并展示Agent对合法变换的选择能力。现有证据不支持独立承诺其超越当前最佳DPA前沿30%。
